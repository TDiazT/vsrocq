# Setting this fork up on a new machine

Written after moving between a macOS/arm64 box and an Arch Linux one. Where the
two differ, both are given; where a step has bitten us, the symptom is recorded
next to it, because every one of these failed in a way that pointed somewhere
else.

## 0. Getting this file onto the machine at all

`AGENTS.md`, `CONTEXT.md`, `docs/agents/` and `docs/adr/` are fork-only tooling
and are deliberately **not** tracked on `staging` — that branch carries only
work destined for an upstream PR. They live on the orphan branch `fork-config`
in this same fork, and are excluded from `staging` through `.git/info/exclude`,
which is per-clone and therefore does not travel either.

On a fresh clone:

```sh
git clone --recurse-submodules git@github.com:TDiazT/RocqLSP.git
cd RocqLSP/vsrocq
git fetch origin fork-config
git show origin/fork-config:docs/agents/exclude >> .git/info/exclude
git restore --source=origin/fork-config --worktree -- AGENTS.md CONTEXT.md docs/agents docs/adr
```

The `restore` writes the files into the working tree without staging them, and
the `exclude` lines keep `git status` quiet about them. Do that in the order
shown: exclude first, restore second, or the files show up as untracked and
invite an accidental `git add .`.

To edit them, work on a `fork-config` worktree and push there — not from the
`staging` checkout, where they are untracked on purpose.

## 1. System packages

**Arch**

```sh
pacman -S opam ocaml gmp pkgconf bubblewrap nodejs npm xorg-server-xvfb
```

`bubblewrap` is what opam sandboxes builds with on Linux; without it `opam
install` fails in ways that read like a network or permissions problem.
`xorg-server-xvfb` provides `xvfb-run`, needed only by the VS Code/Electron
suite (`npm test`), not by the LSP suite.

**macOS** — opam from Homebrew (`/opt/homebrew/bin/opam`); no xvfb, the Electron
suite runs against the real display.

## 2. The opam switch

The switch must be **OCaml 4.14.2 with Rocq 9.2.0**, matching the
`install-opam (ubuntu-latest, 4.14.2, 9.2.0)` cell in `.github/workflows/ci.yml`.
Both halves matter:

- **Not OCaml 5.x.** The SIGBUS workaround in `language-server/dm/proverThreadStubs.c`
  self-disables there: OCaml 5 installs no SIGSEGV handler and the stub's guard
  detects that and stands down. A 5.x switch therefore cannot reproduce any of
  the signal-handling behaviour the stack-overflow tests exercise, and anything
  measured on one is void.
- **Rocq 9.2 exactly.** The golden half of the LSP suite is content-frozen
  against 9.2 (`client/src/test/lsp/README.md`). Another version fails the
  goldens for reasons that have nothing to do with the change under test.

```sh
opam switch create vsrocq-dev ocaml-base-compiler.4.14.2
eval $(opam env --switch=vsrocq-dev --set-switch)
opam install rocq-core.9.2.0 rocq-runtime.9.2.0 rocq-stdlib.9.2.0
opam install ./language-server/vsrocq-language-server.opam --deps-only --with-test
```

A plain switch is enough. `docs/developers.md` tells you to build inside a Rocq
repository checkout ("Composing the build with Rocq"); that is only needed when
modifying the Rocq kernel itself, not for normal work here.

### The PATH trap

Run `eval $(opam env --switch=vsrocq-dev --set-switch)` **before** narrowing
`PATH`, never after. Stripping opam out of `PATH` first makes `opam env` produce
nothing, silently, and the build then picks up whatever other switch is active
and fails with dune errors about a missing `lsp` package — which look like a
dependency problem and are not.

Second trap, on either OS: Rocq 9.x ships `rocq` and no `coqc`. A stray `coqc`
from another switch earlier in `PATH` makes the build compile against the wrong
Rocq API, and the type errors it produces point nowhere near the cause.

## 3. Node

The client needs **Node 24**. Node 20 rewrites `client/package-lock.json`,
dropping the `libc` fields, and then cannot build with vite 8. If the lockfile
shows up modified after an `npm` command, that is what happened.

## 4. Building

```sh
cd language-server && make dune-files && dune build -p vsrocq-language-server
cd ../client && npm ci && npm run gen-vscode-types && npm run build --workspaces
npm run compile-tests
```

`npm run build --workspaces` is not optional before compiling the tests:
`src/package-json.ts` is generated by `gen-vscode-types`, and `pp-display`'s
`types` entry points at a `dist/` its own vite build produces. Skipping it fails
as `Cannot find module './package-json'`. `pretest` does this for you;
`pretest:lsp` does not.

## 5. Running the suites

```sh
cd client
npm run test:lsp          # structural, version-independent — 15 passing
npm run test:lsp:golden   # goldens, pinned to Rocq 9.2 — 8 passing
npm test                  # VS Code/Electron suite; needs xvfb-run on Linux
cd ../language-server && make test   # OCaml inline tests
```

Both LSP suites need a built server. The golden run also needs `rocq` on `PATH`:
one fixture is compiled to a `.vo` at test time, and if the compiler is missing
the `definition` golden fails with a mismatch rather than with a clear error.

`VSROCQPATH` selects the server binary for both suites. `VSROCQARGS` is read by
the structural suite only — the golden suite spawns with a fixed argument set on
purpose, so a golden pins server output and not the environment it ran in.

## 6. What each machine cannot do

- **On Linux:** the macOS-only half of the stack-overflow work is unreachable.
  `knownDecline` recognises a macOS death signature; its unit tests take the
  platform as an argument, so the test file runs fine, but the real behaviour
  cannot be exercised.
- **On macOS:** the Linux SIGSEGV that CI hits in that same test needs an actual
  Linux box. On this Mac, Docker Desktop and the default colima profile do not
  start; `colima start --profile vz-test` does, and it cannot bind-mount
  anything under `/private/tmp`.

## 7. Git workflow

- `staging` is the integration branch, cut from `main`, which tracks upstream.
- **One commit = one PR.** A fix and its test go in the same commit. The check:
  if this commit were a PR on its own, would it stand up? If it has no test, it
  is cut wrong.
- A fix for something a commit on `staging` broke is **amended into that
  commit**, not stacked on top. A commit that breaks the pipeline should not
  reach a reviewer broken.
- `git rebase -i` is not available in the agent harness. Use: detach at the
  target, apply, `git commit --amend`, then
  `git rebase --onto <new> <old> staging`. Take a backup ref first
  (`git update-ref refs/backup/<name> staging`) and push with
  `--force-with-lease`.
- **Never open a PR without explicit permission.**
- Never write `#NNN` in a commit message here; see `issue-tracker.md`.
- After any push to `staging`, bump the `vsrocq` submodule pointer in the parent
  repository (branch `setup`) in its own `chore:` commit, and push that too.

## 8. CI

`.github/workflows/ci.yml` does **not** trigger on `staging` — it listens on
`main`, `coq-master`, tags, `pull_request` and `workflow_dispatch`. Trigger it
by hand:

```sh
gh workflow run ci.yml -R TDiazT/vsrocq --ref staging
```

The fork is public, so runners are free, but the matrix is ~41 jobs across Rocq
8.18–master on Linux and macOS. If a cell fails, narrow to that job
(`gh run rerun --job <id>`) rather than re-running the matrix. `install-windows`
is `if: false` upstream and never runs.

While a run is in progress `gh run view --log` refuses to serve logs; fetch a
finished job's log directly instead:

```sh
gh api /repos/TDiazT/vsrocq/actions/jobs/<job-id>/logs
```
